Headline findings

  • Bedrock is not unconditional. ROADMAP.md says BEDROCK_INVARIANT is emitted in every prompt envelope. In resolver.py:754 it is only queued when a personality node is recalled or persona_prompt is non-empty. Config.persona_prompt defaults to "" (config.py:143). On a stock install with no trait/directive/preference rows, Model A receives no identity text from Strand. This also contradicts the OBS-ONB-009 statement that a fresh session loads the Bedrock. (Code reading only; I did not run a live request.)
  • The bedrock is split across layers. The text is in common.py:52, but its ledger sentinel BEDROCK_ID = -2 and its gating logic are in resolver.py:37, 754. The brief placed BEDROCK_ID in common.py.
  • Strand's persona is prepended, so the client's own system prompt follows it. proxy._inject_delta puts the Strand block first, then \n\n, then the client's text. Where a frontend supplies its own persona, recency favours the client. Strand cannot override it.
  • All fragments are strings pasted inline. There are 9 prompt-bearing definitions across 6 modules. Model B's extractor prompt is one 5.2 KB string literal with roughly 19 negation or restriction words.

Turn 1 vs Turn 2+ (SessionLedger)

Turn 1 (cold session)

  • Ledger empty, so filter_new returns [BEDROCK_ID, PERSONA_ANCHOR_ID?, personality ids, matched entity ids].
  • Full block rendered, then stored by remember_context (session.py:192).
  • Up to 20 personality nodes (MAX_PERSONALITY_ENTITIES) are recalled regardless of query relevance.

Turn 2+ (warm session)

  • Ids already seen are dropped. Bedrock, anchor and personality rows are not re-sent. Only new factual facts, re-flagged discrepancies and new continuity appear.
  • If nothing is new, resolve() returns "" and nothing is injected.
  • replay_context re-prepends earlier blocks that are absent from the client's system text (ERG-CTX-005), so persona survives clients that resend only user/assistant history.
  • Eviction: when stored blocks exceed MAX_REPLAY_CHARS = 12000, the oldest block is dropped and its ids un-seen (session.py:201-207). Turn 1 carries the Bedrock, so it is the first block to go. The Bedrock is re-injected the next time it is queued, so the persona can reappear mid-conversation.
  • ledger.reset on resolution failure or upstream ≥400 clears everything, so the next turn is a cold Turn 1 again.

03Instruction Collision & Precedence Analysis

3.1 Precedence ladder as implemented

1
Client system/developer message positioned last, with no Strand marker; strongest by recency and authorship. Nothing in Strand arbitrates against it.
2
Graph personality rows (trait, then directive, then preference by position, not authority) Model B authored; ORDER BY confidence DESC, then tagged [inferred] below 0.8.
3
Bedrock Invariant listed first in the block, but a one-time injection and the first block evicted from replay.
4
config.persona_prompt cold-boot fallback only. Silently suppressed once any trait/directive/preference exists (resolver.py:750-753).
5
Provider RLHF defaults everything above competes against these.
Nothing in the text tells Model A which tier wins. Precedence is encoded only in section order, so a model that weights later text more heavily may let lower sections override the Bedrock. The Bedrock is called the "permanent identity", yet the code makes it the least durable fragment in the block. Recency weighting is a general tendency, not something I measured on Strand's models.

3.2 Collisions and gaps

C1 · persona_prompt suppression HIGH

The anchor is dropped as soon as one stance node exists (anchor = [...] if persona_prompt and not stance), and stance is evaluated over all recalled entities each turn. An operator-written persona_prompt therefore disappears from new sessions after the first learned preference. Within one session, turn 1 may carry the anchor and turn 3 a new trait, so the context can hold both. The outcome depends on when a rule was learned.

C2 · Bedrock vs. client prompt MED

"Never use corporate filler" is prepended to a client prompt that may demand a polite, structured or verbose assistant (editor frontends, for example). Strand supplies no conflict marker, so the result is undefined and varies per upstream model.

C3 · Bedrock is conditional HIGH

With defaults (persona_prompt="", empty personality graph) Model A gets zero Strand identity text. That contradicts ROADMAP.md (OBS-POL-005 Phase 1) and OBS-ONB-009. The logic is deterministic (resolver.py:752-754), so this is a docs/design discrepancy. Based on code reading; no live request was sent.

C4 · Model B rules reach Model A unreviewed MED

Directive and preference summaries are written by a local SLM, then injected verbatim as instructions. A mis-extraction, such as a transient request stored as a permanent rule, becomes a standing instruction in every future session. The permanence guardrail is prose enforced by SLM compliance. Code-level nets are the confidence tag, deprecation and collapse_containers.

C5 · Contradictory rules can coexist MED

Deprecation needs Model B to reproduce the exact source, target and relation of the old rule (extractors.py:54-57, 63-67). A paraphrased target creates a new node while the old one stays live, so Model A could see "send full files" and "give unified diffs" together. Only nodes whose every edge is dead are dropped (resolver.py:730).

C6 · Operator anchoring LOW

Rules link to "the entity User"; telemetry uses "the declared name, else User". reanchor_generic_user later folds User into the named operator and keeps it as an alias, so rule edges may briefly hang off two nodes. telemetry_preference reads only person sources and tolerates this.

C7 · Reality-check imperative repeats LOW

"Clarify or challenge this discrepancy" is re-sent each time the query repeats the clash and bypasses the ledger (resolver.py:761-762). That is intentional, but it can push toward an interrogative cadence that works against "direct, plain-spoken".

C8 · Tool note points at absent context LOW

Four tool descriptions say to answer hardware questions "from the ambient host context". My grep found no host-context block injected by proxy.py or resolver.py; get_host_context is used by extractors.py (hostname only) and the UI bridge. The instruction may therefore reference context Model A never receives. Confirmed by grep, not by a live request.

3.5 Model B: permanence, deprecation, operator anchoring

How preference extraction behaves
  • Permanence markers: explicit list ("from now on", "always", "never", "stop doing X", "switch to Y", "going forward"). Transient steering ("right now", "just for this", "give me the diff") must return nothing and must not deprecate. Markerless corrections such as "actually, stop using diffs, send full files" are handled in a separate paragraph (extractors.py:54-57), which overlaps the permanence rule. The prompt does not say which paragraph wins for "actually" without a marker. ambiguity
  • Deprecation: severs edges only and never deletes entities (:68). The exact (source, target, relation) must be reproduced. ARCHITECTURE.md also documents a heuristic fallback for basic negation in the distill layer (I did not read distill.py itself).
  • Biography guard: past possessions become active previously_owned edges, never deprecations (:36-41). A strict boundary that costs many prompt tokens.
  • Operator anchoring: rules attach to "the entity User" using prefers / demands / enforces. The prompt text itself says the model_inferred origin is applied automatically (:66-67). Compaction-inferred traits use MODEL_CONFIDENCE = 0.6 and relations limited to prefers|enforces (compactor.TRAIT_RELATIONS), so they surface tagged [inferred].
  • Telemetry stance: the provenance guard is in code (onboarding.telemetry_preference: Enabled needs user_explicit at confidence ≥ 1.0 on both edge and source). The prompt can only propose an edge, and a model-inferred Enabled edge cannot open telemetry. This is a good example of safety enforced outside the prompt.

04Architectural Recommendations

4.1 Consolidating prompt contracts into src/strand/prompts.py

Analysis only. This audit is read-only and nothing was implemented.

Case for

  • 9 prompt-bearing definitions sit in 6 modules; two are 1-5 KB string literals inside modules whose job is parsing and I/O.
  • Duplicated contracts have no shared constants: the archetype enum (common.py vs extractor prose), the telemetry entity names (onboarding.py vs extractor prose), and the "transient vs sustained" concept (extractor vs compactor).
  • One file makes token budgeting and prompt-change review a single-file job, and lets one test assert a global budget.
  • common.py must not import other strand modules; a stdlib-only prompts.py at the same level adds no cycle risk.

Cost / risk

  • Tests reference extractors.SYSTEM_PROMPT and compactor.SYSTEM_PROMPT by name in places (I did not enumerate every reference). Re-exports keep them green; tests must not be loosened.
  • Moving prose verbatim is safe; any rewording changes SLM behaviour and needs extraction fixtures.
  • Tool descriptions interpolate handler constants (MAX_READ_LINES etc.), so they are better left beside their handlers or built from prompts.py with values passed in.
  • It adds a module but no dependency, consistent with the charter's "surgical, no frameworks" rule.

4.2 Preserving peer-level cadence and formatting restraint without stacking

R1 · Make the Bedrock's status explicit

Decide whether the documented behaviour (always emitted) or the coded behaviour (conditional) is intended, then align code and docs. If it should always be emitted, queue BEDROCK_ID regardless of stance or anchor. A cold install currently gets no identity.

R2 · One positive cadence description

Replace the stacked "Never apologize / Never use filler" with a positive description of the target register (answers first, uncertainty stated once, plain prose by default) and keep at most one hard prohibition. Positive anchors often generalise better than prohibition lists. That is a design hypothesis: validate it with before/after samples on the intended frontier models.

R3 · State precedence once, in the text

One header line saying operator rules override defaults, and the client's system message governs task format only, would replace implicit ordering and resolve C2 explicitly. Cost: roughly 25 tokens, once per session.

R4 · One owner for formatting restraint

Formatting restraint currently exists only as learned preference rows. If it is a product default it belongs in the Bedrock and the extractor should not re-learn it; if it is learned, keep it out of the Bedrock. Do not state it in both places.

R5 · Tier the extractor prompt

Split the 769-word literal into (1) output schema, (2) a few decision rules, (3) short worked examples. Drop prose that code already enforces (container collapse, telemetry provenance). A shorter prompt for a small local model reduces gate collisions. Measure on a fixed extraction fixture set before and after.

R6 · Deduplicate tool boilerplate

SCOPE_NOTE is repeated on 4 tools (about 270 tokens per request). State it once, and resolve C8 by either injecting the host context it refers to or rewording the note.

R7 · Bound the always-on rule set

Up to 20 personality nodes are injected on turn 1 regardless of relevance. A token-based cap plus a contradiction check (same relation family, different target) at injection time would reduce C5 without adding prompt prose.

R8 · Test budgets, not wording

Add a budget test over the assembled envelope (Bedrock + 20 nodes + tool schemas under N tokens) instead of snapshotting prompt text. Existing tests stay intact and stacking is caught before it ships.
